# Connected mail release review (default off)

**Implemented, not enabled or deployed.** `CONNECTED_MAIL_ENABLED` defaults off; each provider also requires its own server-only client ID/secret, `MAIL_TOKEN_ENCRYPTION_KEY` and canonical `APP_ORIGIN`. Apply `lib/db/deploy/20260925-connected-mail-oauth.sql` only through reviewed PostgreSQL release after the owner-foundations migration. The local SQLite schema is for fresh dev/test databases; an existing local SQLite database needs recreation/migration. No real provider calls were made in development.

## Consent and boundary

The owner must have current product access, a non-demo household and explicit separate provider consent. Authorization uses canonical APP_ORIGIN callback, exact path/origin, short-lived one-use server-side state, encrypted PKCE verifier and SameSite/HttpOnly state cookie; callback verifies current signed-in owner and provider account identity (`sub` + verified email for Google, Graph `/me.id` for Microsoft), binds an HMAC account ID and never accepts browser-asserted tokens. Accounts are not interchangeable; reconnecting a revoked account requires new consent. Tokens are AES-256-GCM encrypted, never exposed to browser, and refresh/rotation uses compare-and-swap. Encryption-key version is currently v1; key rotation/re-encryption needs operational tooling before any key change. A multi-key decryption plan is required for zero-downtime rotation.

`gmail.readonly` is required because the lesser `gmail.metadata` scope **does not permit `q` sender filtering**. Gmail list queries are narrowed to an approved sender domain and a bounded time interval; only `format=metadata` with From and Date headers is fetched; local exact-domain verification discards false positives. Microsoft uses delegated `Mail.ReadBasic` + `User.Read`, sender/date-scoped Graph `$search`, `$select=id,from,receivedDateTime`, and a validated continuation URL; no bodies, attachments or previews are requested. Provider search semantics and permissions need actual tenant/sandbox staging tests. An approved domain is the intersection of active curated policy, verified sender and a recently verified official institution source. If there are no approved domains, no mailbox API call occurs. Sending headers are not sufficient authentication proof; HTTP adapters set `authenticated=false` so retained minimal evidence is quarantined, never automatically closes a task or certifies research. The separate old forwarding validation workflow is unchanged.

The sync cursor stores per-domain pagination and a rolling 24-hour overlap, starts at 30 days, processes at most 50 metadata envelopes per invocation, and deduplicates keyed message digests. It rechecks sender approval before persistence and rejects stale connection checkpoints. Rate/5xx/timeouts use a persisted retry-after; invalid grant requires re-consent. Owner manually triggers sync; **there is no background sync scheduler**. Schedule `purgeMailRetention()` before activation: evidence/sync events 30 days, OAuth attempts after ten minutes, control audit 90 days; disconnected rows deleted on purge. The authenticated `POST /api/mail/maintenance` route is ready for an external daily scheduler with a 32+-character `MAIL_MAINTENANCE_SECRET`; no schedule or secret is configured. Alerting/operational retry policy remains required for production automation.

Disconnect attempts Google refresh-token revocation then immediately erases local tokens and evidence even on remote failure. Google failure needs user removal at Google Account > Security > Third-party connections. Microsoft does **not** provide a per-app refresh-token revocation endpoint using these delegated least-privilege scopes; obtaining broad `DelegatedPermissionGrant.ReadWrite.All` or `User.RevokeSessions.All` would affect more than this grant and is intentionally not requested. Local disconnect erases all tokens and evidence, tells the user to remove this grant at `https://myapps.microsoft.com/`, and records `manual_required`. Thus the requested automatic **remote revocation for Microsoft is not achievable under least privilege**; a reviewed alternative or explicit release exception is necessary before enabling. Household account deletion calls connected-mail erasure before deleting the household when enabled or when an existing grant remains. `/account/mail-privacy` keeps disconnect/delete available to a signed-in owner after product access expires or the feature flag is turned off.

## External setup / release gates

- Google Cloud: consent-screen registration, exact HTTPS callback, Gmail API, OAuth client secret, requested `gmail.readonly` restricted-scope app verification, privacy-policy/domain verification and potentially annual independent security assessment for restricted Gmail data storage/transmission. Confirm Google Data API policy and production-use authorization.
- Microsoft Entra: app registration with exact callback, delegated `Mail.ReadBasic`, `User.Read`, `offline_access`, multitenant/single-tenant policy decision, tenant/admin consent where required and publisher verification when relevant. Validate Graph search behavior and pagination against actual Exchange Online mailbox; consumer account support is not promised.
- Security/privacy: threat model, key management/rotation, consent wording, DPA/data deletion and retention policy, narrow sender curation, backoff/telemetry, scheduler, account-deletion failure handling, live OAuth state-cookie browser round trip, staging mailbox false positives and actual remote revocation observation. Do not enable flag, configure secrets, or deploy as part of this change.
